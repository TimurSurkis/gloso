# Звонки, пилот и уведомления

Статус: **проект v0.1**. Согласованные правила: D-009–D-010, D-018–D-020, D-028–D-039, D-051–D-053, D-056, D-060–D-065, D-069. Конкретные протоколы провайдеров ещё проверяются.

## 1. Маршрут нового звонка

Переадресация при неответе примерно через 10 секунд или занятой линии, включая нерабочее время. У каждого автосервиса отдельные номер Twilio и агент ElevenLabs.

До запуска AI проверяются доверенная привязка, административная пауза, ручная активация пилота, срок, доступные минуты и активные разговоры tenant. Без результата проверки — AI не запускается. Нативная интеграция ElevenLabs с Twilio, которая подключает агента в обход backend, не удовлетворяет этому требованию; маршрут должен проходить проверку допуска до старта AI.

| Причина                                        | Требуемое поведение                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------- |
| AI уже занят разговором этого автосервиса      | Сообщение о занятости средствами телефонии, завершение, без очереди |
| Пилот не активирован/окончен, минуты исчерпаны | Нейтральное сообщение телефонии и завершение, без внутренних причин |
| Невозможно проверить допуск                    | Fail-closed, сообщение телефонии независимо от backend              |
| Calendar на сверке                             | AI может принимать новые Relay-заявки при прочих разрешениях        |

Не возвращать отказавший маршрут автоматически на исходный номер с переадресацией. Не считать голосовое сообщение телефонии новой AI-сессией или бесплатной телефонией.

## 2. Допуск и активность

Проект алгоритма допуска:

1. Проверить подлинность серверного события, его возраст и привязку к tenant. Нельзя доверять одним аргументам LLM.
2. В короткой транзакции под tenant-блокировкой найти предыдущий допуск. Повтор возвращает прежнее решение и не запускает вторую сессию.
3. Проверить pilot/access и лимит разговоров (начально 1); создать индивидуальный допуск с внутренним случайным `call_id`.
4. Зафиксировать состояние до разрешения подключения AI. Повторно использовать завершённый/отклонённый допуск для новой сессии нельзя.

Проект учёта бюджета на допуске: атомарно учитывать индивидуальный резерв минимум одной минуты, который заменяется фактическим расходом при завершении. Это инженерное предложение для будущей параллельности, а не гарантия жёсткого потолка 40 минут. Значение/механизм резервов ещё требуется проверить в тестах.

Максимум разговора — начально 180 секунд с настройкой. Lease/тайм-аут строки не доказывает, что удалённый разговор завершился. До проверки активности или подтверждённой гарантии провайдера нельзя освобождать единственную ёмкость и создавать второй разговор только по локальному TTL. Потерянное завершающее событие требует сверки/безопасного ручного решения, не нулевой стоимости.

## 3. Пилот и расход

- Пилот активируется вручную; создание tenant и первый звонок его не запускают.
- Окончание — через 14 календарных дней в то же местное время Europe/Warsaw. Предлагается при неоднозначном/несуществующем локальном окончании возвращать администратору явную ошибку настройки, а не молчаливый сдвиг; правило требует ревью.
- Все фактически подключённые разговоры учитываются, включая прерванные, ошибочные обращения и спам.
- Списание `ceil(ai_seconds / 60)`, нулевое время — ноль минут, ожидание до AI исключено.
- Завершение атомарно закрывает только свой допуск и однократно увеличивает агрегат. Дубликат не увеличивает расход.
- При исчерпании/конце срока новые сессии запрещены; активная заканчивается штатно в рамках отдельного максимума разговора. Возможен перерасход.
- Ручная пауза не останавливает течение пилота и не сбрасывает расход. Возобновление не отменяет другие запреты.

Уже допущенный разговор продолжает использовать инструменты в рамках своего жизненного цикла: нельзя отказать ему только потому, что во время разговора закончился пилот/баланс. Проверка нового допуска и полномочия действующей сессии — разные проверки. Завершённая сессия не получает право начинать новые действия по старому `call_id`.

Источником длительности не являются аргументы агента или время доставки webhook. Позднее/корректирующее событие, завершение без допуска и события старше окна состояния обрабатываются по отдельным проверенным правилам. Предлагается не списывать старое событие автоматически после удаления дедупликации, а сигнализировать о необходимости разбора. Не объявлять пропущенный конец нулевым расходом.

Платежи, новые платные периоды, продление пилота/пополнение минут/сброс сейчас не реализуются.

Возврат минут за технические сбои Gloso в первом релизе не реализуется (D-075), но модель расхода отделена так, чтобы позволить добавление корректировок позже без сброса пилота.

## 4. SMS сотруднику

Один назначенный получатель на tenant. Контакт звонящего может отличаться от Caller ID; он нормализуется/валидируется как польский, но не считается подтверждённым. SMS звонящему не отправляются.

Calendar-уведомление формируется после доказанного создания визита. Relay-уведомление явно обозначает неподтверждённую заявку/время. Обязательные поля: имя, контакт, марка/модель, проблема; пожелание времени, включая «любое». Формат и объём SMS зависят от реальных ограничений Twilio: кодировка, сегментация, доступный отправитель в Польше и цена. Эти ограничения не выдумываются и проверяются в [трекере](../trackers/track-backend-validation.md).

| Результат SMS adapter               | Действие                                                                     |
| ----------------------------------- | ---------------------------------------------------------------------------- |
| Подтверждённое принятие провайдером | Не отправлять повторно; не называть доставкой сотруднику                     |
| Временный отказ без принятия        | Ограниченные повторы из памяти с увеличением задержки                        |
| Постоянный отказ                    | Прекратить повторы, технический сигнал администратору                        |
| Неизвестный исход                   | Не повторять вслепую; сверка/идемпотентность только при доказанной поддержке |

Предлагаемые локальные технические значения: до 3 попыток суммарно, задержки 1 и 3 секунды для гарантированно не принятых попыток. Это **проектные значения для тестов**, не подтверждённые условия Twilio. HTTP-ошибка сама по себе не доказывает, что отправка не принята. Принятие/постановка в очередь не равны доставке сотруднику; доставка подтверждается только если реальный status callback это доказывает.

Получатель фиксируется для логической отправки; изменение конфигурации во время повтора не должно незаметно перенаправить содержимое другому сотруднику. Текст/контакт не пишутся в долговечное состояние. При падении процесса попытки теряются, восстановления отправки нет. Подтверждённый технический результат хранится отдельно для предотвращения повторного действия.

При окончательной ошибке Calendar-визит остаётся подтверждённым; статус уведомления отдельно. Relay не возвращает успех при отказе/неизвестном исходе.

## 5. Telegram администратору

Технические события: окончательный сбой SMS, неизвестный исход Calendar/ручная сверка, переход пилота к окончанию/исчерпанию. Другие категории добавляются явно, а не через отправку произвольного stack trace.

Предлагаемый payload: технический код tenant, категория, безопасный код ошибки, признак требуемой проверки. Без имени/телефона/автомобиля/времени визита, текста, сырых webhook, токенов и сырых ошибок. Достаточно ссылки на tenant для получения деталей через защищённый admin API; глубокая ссылка не должна содержать административный секрет.

Один логический сигнал на переход пилота, не на каждый последующий звонок. Exactly-once доставка внешнему Telegram не обещается: повтор/сбой отправки может дать неопределённость. Механизм дедупликации, ограничения частоты и ограниченных попыток ещё проверяется. Telegram не является единственным способом заметить неработающий backend: нужны внешние health checks/мониторинг.
