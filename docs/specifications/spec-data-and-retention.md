# Данные, техническое состояние и ретенция

Статус: **проект схемы v0.1**, не готовые миграции. Основания: D-006, D-040–D-043, D-062, D-066. Согласованная допустимость категорий не означает автоматического утверждения каждого поля ниже.

## 1. Разделение категорий

| Категория | Назначение | Хранение |
| --- | --- | --- |
| Конфигурация | Настройки автосервиса/получателя/интеграций | PostgreSQL; срок после прекращения обслуживания ещё определить |
| Доступ и расход | Активация, окончание, пауза, агрегат минут | PostgreSQL; не удаляется автоматически по сроку аудита |
| Операционное состояние | Допуск, дедупликация, неизвестные результаты, владение | Проектно до 7 дней; обоснование окна проверяется на провайдерах |
| Аудит | Подтверждение факта AI-разговора, грубые время/длительность и итог | Зашифрованно, не более 30 дней от окончания |
| Содержимое обращения | Имя, контакт, автомобиль, проблема, время визита, SMS | Только оперативная память текущей операции/ограниченных повторов и внешние адресаты |
| Секреты | Токены API, ключи Google, HMAC и шифрования | Отдельное хранилище секретов/секреты окружения |

Не сохранять запрещённое содержимое в result JSON, encrypted JSON, хеше текста заявки, исключении, SQL-логах, дампе памяти, очереди или трассировке. Шифрование не превращает содержимое в разрешённый аудит.

## 2. Предлагаемые таблицы

### `tenants`

`id`, название, режим `CALENDAR|RELAY`, административная пауза, номер Zadarma, ID агента ElevenLabs, ID календаря, телефон назначенного сотрудника, ссылка на профиль учётных данных, версия конфигурации, временные метки конфигурации.

Параметры расписания/политики могут быть строгими JSONB: недельные интервалы, исключения, политика праздников, minimum lead, horizon, slot step, buffer. Нельзя размещать в них данные обращений. Уникальность номера/агента защищает однозначное сопоставление с автосервисом. Calendar ID обязателен в режиме Calendar.

### `services`

`id`, `tenant_id`, название, длительность, признак доступности для новых записей. Комплекс — отдельная услуга с собственной длительностью. Цены, клиентские автомобили и история визитов не добавляются автоматически.

Рекомендуется отключать услугу, а не разрушать ссылки незавершённых операций. Идентификатор услуги одного tenant нельзя обновлять через другого.

### `pilot_usage`

`tenant_id`, момент ручной активации, момент окончания, лимит минут (40), использованные целые минуты (0). Даты активации/окончания относятся к состоянию доступа, не к времени визита.

Не вводить платёжные поля «на будущее». Административная пауза отделена от расхода/срока. Повтор активации не сбрасывает расход и не начинает новый пилот.

### `call_sessions`

Внутренний случайный `call_id`, `tenant_id`, ограниченные технические привязки провайдеров, состояние допуска/активности, флаг однократного учёта, списанные минуты, связь с единственной логической операцией, краткоживущая связь с аудитом, технические сроки.

Предпочтение — непрозрачные HMAC-ключи вместо сырых внешних ID, если исходный ID не нужен для проверенной серверной операции. Хеши/HMAC телефона, имени или описания не использовать как замену запрещённым данным. Если реальному API нужна ссылка на сессию для проверки её активности, её необходимость и состав явно фиксируются до реализации.

Технические метки допуска/lease/истечения могут быть точными, когда это необходимо для алгоритма. Такая строка и её связь с аудитом остаются потенциально псевдонимизированными; они не являются «анонимным аудитом». Не сохранять точные секунды длительности ради удобства, если для учёта достаточно однократно вычисленных минут и признака обработки.

### `operations`

Непрозрачный серверный ключ, `tenant_id`, тип (`BOOKING`, `RELAY_SMS`, `BOOKING_SMS`), внутренний статус, необходимая внешняя ссылка, исходный Calendar reference для сверки, родительская техническая операция, версия владения, технические сроки.

Внутренние статусы предлагаются `PENDING|COMPLETED|FAILED|UNCERTAIN`. Это **не статусы результата аудита**. Сохраняемый результат — строго разрешённые коды и статус принятия SMS, без времени визита, контакта, текста, токена или полного HTTP-ответа.

Ключи бронирования зависят от канонических технических полей слота/звонка; сохраняется только непрозрачный ключ, не исходные времена. Relay имеет стабильный ключ логической операции звонка, не хеш персонального содержимого.

### `booking_gates`

Одна строка на автосервис: `IDLE|BUSY|RECOVERY_REQUIRED`, ссылка на операцию пока разрешён срок, владелец/версия/lease. В таблице нет времён визитов и содержимого заявок.

Истечение lease не освобождает gate автоматически. При удалении неразрешённой операции очищаются её ссылки/ID, но остаётся минимальное tenant-состояние `RECOVERY_REQUIRED` до безопасной ручной сверки. Это остаточное состояние без ссылки на звонок не объявляется той же семидневной строкой операции; его срок/юридическое описание требуют отдельной проверки.

### `audit_logs`

Предлагаемый минимум: случайный `audit_id`, `tenant_id`, часовой интервал, зашифрованные списанные минуты и результат, часовая граница истечения. Привязка к tenant нужна для отчёта по автосервису, но точный полный состав поля ещё подлежит ревью.

- Результат строго: «запись создана», «Relay передан», «ошибка» либо отсутствие.
- Если длительность ещё неизвестна, не подменять её нулём: предлагается временно незаполненное значение до проверенного завершения.
- Не включать внешний call ID, ключ бронирования, время визита, service description или данные звонящего.
- Краткоживущая связь идёт из `call_sessions`; не создавать другую бессрочную цепочку восстановления идентификаторов.
- Не использовать автоматический точный `created_at`/`updated_at` на строке аудита. Возвращаемое время соответствует часовому интервалу.

Предлагается AES-256-GCM со случайным nonce; идентификатор ключа и версия формата обеспечивают управляемую ротацию. Контекст строки привязывается через authenticated additional data. Шифрование обеспечивает конфиденциальность/целостность, но не независимое доказательство факта звонка или анонимность.

### Дополнительное техническое состояние

Дедупликация Telegram-сигнала о переходе пилота и минимальная история административных действий не являются аудиозаписями или клиентским аудитом. Если нужны отдельные таблицы, их поля/сроки должны быть явно добавлены в спецификацию, а не спрятаны в произвольный JSON. Не сохранять полный diff конфигурации с телефонами и секретами.

## 3. Аудит и подтверждение факта звонка

Разрешение запустить AI не доказывает, что разговор состоялся. Основание аудита — проверенное событие фактического подключения/завершения AI, доступность которого проверяется в интеграции. Backend не загружает аудио/транскрипцию ради подтверждения.

Предлагается часовой интервал завершения. Пока завершение неизвестно, используется консервативный интервал первого подтверждённого AI-события. Позднее завершение может уточнить запись только при живой разрешённой связи и неистёкшем аудите; просроченный аудит не воскрешается.

Точность интервала — не полная анонимность. Источник провайдера, конфигурация tenant, редкий исход, длительность, сроки и внешние журналы могут обеспечивать косвенное сопоставление. Цель аудита — ограниченное техническое подтверждение, не доказательство содержания разговора.

## 4. Сроки и удаление

- Техническое окно отсчитывается от первого принятого события/создания операции, не продлевается повторами. Семь дней — верхняя проектная граница, не гарантия обработки любого позднего события.
- Аудит нельзя читать после `expires_at` независимо от физической очистки.
- Предлагаемая консервативная граница: начало UTC-часа проверенного завершения + 30×24 часа. Она не раскрывает точную минуту окончания и не превышает 30 суток от него. Если завершение неизвестно — от первого подтверждённого AI-события; точное приведение к окончанию тогда не гарантируется.
- До удаления незавершённой операции её gate переводится в `RECOVERY_REQUIRED`, ссылки/владение очищаются. Новые бронирования не разрешаются от одного истечения срока.
- До открытия восстановленной БД выполняется очистка истёкших данных. Рестарт/backup не обнуляет usage и не создаёт новый период дедупликации старого события.
- Политика резервных копий и хранения конфигурации после отключения клиента ещё не выбрана. Автоматический каскадный `DELETE tenant` не предлагается как обычная административная операция.

**Блокер пилота:** периодический worker внутри приложения не гарантирует физическое удаление ровно к сроку при простое. Требуются проверенные настройки независимой очистки, PostgreSQL/Neon backup/PITR и восстановления; если строгие гарантии физического удаления недостижимы, нельзя заявлять, что они выполнены. Обновление юридических документов выполняется после определения фактической политики, не вместо её реализации.
