# Проект HTTP API Gloso

Статус: **собственные нормализованные контракты v0.1, не готовая реализация**. Это не фактический формат webhook Twilio/ElevenLabs. Их адаптеры допускаются только после проверок из [трекера](../trackers/track-backend-validation.md).

## 1. Общие правила

- JSON over HTTPS; строгая Zod-валидация, ограничение размера тела.
- Раздельная защита admin, tools и provider events. Admin-токен не передаётся агенту.
- Tenant и сессия определяются проверенным серверным контекстом. Произвольные `tenant_id`, `agent_id`, `call_id` в аргументах инструмента не дают полномочий.
- Возвращать минимальные коды ошибок, не тела/тексты провайдеров. Не логировать request/response body.
- `400` — форма входа, `401/403` — полномочия, `404` — недоступный ресурс в своём контексте, `409` — конфликт состояния, `429` — ограничения частоты, `503` — недоступность зависимости/готовности. Управляемый бизнес-исход может быть `200` с явным статусом.
- Статусы HTTP/business API не равны трём значениям аудита.

## 2. Административные операции

Предлагаемый заголовок `Authorization: Bearer <admin-token>`; точный формат до реализации проходит ревью. Только администратор Gloso.

| Метод и маршрут | Назначение |
| --- | --- |
| `POST /admin/tenants` | Создать конфигурацию без автоматического запуска пилота |
| `GET /admin/tenants/:id` | Прочитать свою административную конфигурацию |
| `PATCH /admin/tenants/:id` | Режим, привязки, получатель; не подменять исходные ссылки незавершённой операции. Смена режима CALENDAR ↔ RELAY разрешена свободно в любой момент, не затрагивает существующие события Google Calendar и не сбрасывает RECOVERY_REQUIRED (D-071). |
| `PUT /admin/tenants/:id/services` | Проверяемое изменение каталога, без изменения чужих ID |
| `PUT /admin/tenants/:id/schedule` | Недельные интервалы, исключения и параметры поиска |
| `POST /admin/tenants/:id/pilot/activate` | Ручная однократная активация; повтор не начинает новый пилот |
| `PUT /admin/tenants/:id/admission` | `{ "paused": true/false }`, без изменения срока/расхода |
| `GET /admin/tenants/:id/status` | Доступ, расход, активность и необходимость восстановления |
| `GET /admin/tenants/:id/operations` | Только разрешённое техническое состояние в срок хранения |
| `POST /admin/tenants/:id/recovery/check` | Запросить безопасную сверку неизвестного Calendar-исхода |
| `POST /admin/tenants/:id/recovery/resolve` | Защищённая ручная процедура по условиям восстановления, не слепой reset |
| `GET /admin/tenants/:id/audits` | Только неистёкшие минимальные проекции аудита |

`recovery/resolve` нельзя реализовать как безусловное присвоение `IDLE` по boolean-полю. Требуются проверки текущего состояния/версии и достаточное основание исхода. Точный контракт ещё проектируется в [процедуре](spec-booking-recovery.md).

Не добавляются endpoints оплаты, пополнения/продления, сброса минут, клиентского входа/OAuth, архива визитов/транскрипций, переноса/отмены или обычного каскадного удаления tenant.

## 3. Общий объект обращения (только память)

Предлагаемая форма, не разрешение хранить её:

```json
{
  "client_name": "<имя>",
  "contact_phone": "+48<9 цифр>",
  "vehicle": { "make": "<марка>", "model": "<модель>" },
  "problem_description": "<описание>"
}
```

Backend принимает любой валидный международный номер в формате E.164 (для Calendar и Relay). Локальный 9-значный номер без кода страны нормализуется с дефолтным кодом +48. Список разрешённых стран задаётся конфигурацией (по умолчанию открыт, под будущую Фазу 2).

Фамилия и регистрационный номер не добавляются в обязательные поля. Ограничения длин/размера и поддержка типов польских номеров ещё согласуются при проверке библиотеки; не считать одной регулярки доказательством существования телефона.

## 4. Инструменты агента

Предлагаются POST endpoints. Доверенный контекст передаётся не в JSON-аргументах LLM, а через проверяемое session binding. Реальный способ ещё блокирует production; в локальных тестах допустим явно тестовый resolver, который невозможно включить в live-режиме.

### `POST /tools/context`

Пустые аргументы. Возвращает режим текущего обращения, текущее местное время/часовой пояс, разрешённые услуги и их ID/длительности, текущие возможности. Не возвращает секреты, список чужих tenant или архив звонков.

### `POST /tools/availability`

Предлагаемый вход: `service_id`, явный `range_start`, `range_end` с однозначными моментами. Возможность запроса «любое» означает поиск в допустимом горизонте, не произвольную дату создания.

Результаты: `SLOTS_AVAILABLE` со слотами `{slot_id, start_at, end_at}`, `NO_SLOTS`, `RELAY_REQUIRED`, `RETRYABLE_ERROR`/недоступность по контракту. Причина Relay — разрешённый код: режим, Calendar недоступен/на сверке, неизвестная услуга или длительность. No-slots разрешает отдельный Relay по D-054.

### `POST /tools/bookings`

Вход: `slot_id` и объект обращения. Сервер проверяет контекст, подпись, срок, конфигурацию, услугу, график, доступность и единственный результат звонка. Значения времени не интерпретируются повторно из относительных слов.

Предлагаемые бизнес-результаты: `BOOKED`, `SLOT_CONFLICT`, `STALE_SLOT`, `PENDING_VERIFICATION`, `CALENDAR_UNAVAILABLE_BEFORE_CREATE`, `CALL_ALREADY_HANDLED`. У `BOOKED` отдельный `notification_status`, не смешанный с результатом брони.

Ответ `BOOKED` допустим только после подтверждённого создания. `PENDING_VERIFICATION` не разрешает новый insert или дублирующий Relay. Повтор успешно завершённой операции возвращает прежний технический результат без внешнего действия.

### `POST /tools/relay`

Вход: объект обращения, `preferred_time` как `{ "kind": "ANY" }` либо `{ "kind": "REQUEST", "text": "<пожелание>" }`. Поле остаётся в памяти и тексте SMS, не в БД. «Любое» не приравнивается к отсутствующему ответу.

Предлагаемые результаты: `RELAY_ACCEPTED_BY_PROVIDER`, `RELAY_FAILED`, `PENDING_VERIFICATION`, `CALL_ALREADY_HANDLED`. Принятие провайдером не означает доставку или подтверждение времени визита. После успеха другой независимый Relay/Calendar в том же разговоре не начинается.

## 5. Нормализованные события и допуск

Слой провайдеров вызывает внутренние сценарии:

- `admitCall(trustedIdentity)` — до подключения AI; на маршруте Twilio это должно происходить до старта агента ElevenLabs;
- `confirmAiConnected(trustedEvent)` — подтверждение фактического AI-подключения, не равное разрешению допуска;
- `completeCall(trustedEvent)` — длительность/однократный расход/закрытие активности;
- подтверждение статуса SMS — только если реальный контракт Twilio позволяет достоверную привязку.

Локальный тестовый HTTP transport может предоставлять `/internal/test/calls/admit`, `/connected`, `/complete` с отдельным тестовым секретом и фиктивными metadata. Он **не существует в live-конфигурации**. Фактические публичные callback routes и подписи задаются отдельными provider adapters после проверки примеров событий.

Аутентификация события не делает всю его форму разрешённой к хранению. Нельзя сохранять сырой body ради последующей перепроверки. Для Twilio проверка подписи запроса, набор status callbacks и повторы доставки ещё не подтверждены; для ElevenLabs отдельно требуется найти технические события без получения backend аудио/транскрипций.

## 6. Health и администрирование данных

Предлагаются `GET /health/live` (процесс) и `GET /health/ready` (готовность принимать работу). Ответы не раскрывают credentials, tenant-конфигурации и обращения. Readiness false до обязательной стартовой очистки и при невозможности гарантировать допуск.

Аудит читается с фильтром срока непосредственно в запросе; pagination не становится постоянным экспортом содержания. Полные технические тела операций/провайдеров не предоставляются ни через «debug», ни через status.
