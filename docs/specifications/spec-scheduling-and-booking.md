# Расписание, слоты и создание визита

Статус: **проект v0.1** на основе D-011–D-016, D-044–D-050, D-054, D-057–D-059, D-063–D-064, D-067, D-072, D-073. Согласованные числовые параметры отделены от предлагаемых алгоритмов.

## 1. Источники истины

- Конфигурация автосервиса: услуги/длительности, рабочие интервалы, исключения и параметры поиска.
- Google Calendar: фактическая занятость и созданные визиты. Копии визитов в PostgreSQL не создаются.
- Все операции интерпретируют местное время в Europe/Warsaw; хранить/сравнивать моменты предлагается в UTC, не с фиксированным смещением.

Начальные параметры: минимум до начала 60 минут, горизонт 14 дней, шаг 30 минут, буфер 0. Параметры изменяемы для автосервиса. Полная длительность выбранной услуги обязательна; тестовое одинаковое значение не становится бизнес-правилом.

## 2. Проект модели расписания

- Недельное расписание: дни ISO `1..7`, список локальных интервалов `HH:mm`.
- Исключение на дату `YYYY-MM-DD`: закрыто либо список рабочих интервалов.
- Предлагаемый приоритет: явное исключение даты → государственный праздник при включённой политике → недельное расписание.
- Предлагается запрещать пересекающиеся интервалы и интервалы через полночь; при необходимости ночной работы потребуется отдельное правило, а не молчаливая интерпретация.
- Слот должен целиком помещаться в одном рабочем интервале и не занимать обеденный перерыв.

Праздники: польские государственные нерабочие даты автоматически закрыты, конкретную дату можно открыть исключением. Источник/версия набора дат и обновление изменений закона ещё проверяются. Не подменять государственными праздниками каникулы или неофициальные памятные даты.

## 3. Даты и ограничения

Проект собственных инструментов принимает явные диапазоны дат/времени, а не разрешает backend произвольно трактовать неограниченный текст. Агент получает текущее местное время и часовой пояс из backend. Возможность нужного server-side контекста проверяется отдельно; промпты сейчас не пишутся.

Предлагаемые правила:

1. Неоднозначное пожелание уточняется, а не превращается в случайный слот. Невалидные и несуществующие местные часы не принимаются.
2. Для повторяющегося часа при переводе времени требуется однозначный момент/UTC-смещение; одинаковая надпись часов не означает один и тот же слот.
3. Граница горизонта (D-074): от текущей местной даты до конца даты today + horizon_days включительно в Europe/Warsaw.
4. Проект горизонта — от текущей местной даты до конца даты `today + horizon_days`, включительно; это конкретизация для ревью, не отдельно подтверждённое владельцем правило границы.
5. По согласованному D-067 окончание пилота ограничивает запуск AI, но не дату визита: во время активного пилота разрешено создать визит после его окончания, если дата входит в горизонт. Окончание пилота не удаляет созданный визит из календаря.

## 4. Расчёт слотов

Проект алгоритма:

1. Получить проверенный tenant/call-контекст и одну услугу текущего каталога.
2. Если услуга/длительность неизвестна или не настроен нужный комплекс — вернуть доступность Relay. Не суммировать времена самостоятельно.
3. Построить разрешённые интервалы по расписанию и исключениям в Europe/Warsaw.
4. Прочитать занятость Calendar. Предлагается использовать занятые интервалы Google, включая ручные/повторяющиеся/целодневные события, и не блокировать время прозрачными событиями. Точное поведение API проверяется отдельно.
5. Рассматривать интервалы как полуоткрытые `[start, end)`: при нулевом буфере конец предыдущего равен началу следующего без конфликта.
6. Кандидаты начала — сетка от 00:00 местных суток с настраиваемым шагом (начально 30 минут).
7. Для кандидата `end = start + duration`. Проверить полное попадание в разрешённое время и отсутствие конфликтов.
8. Буфер только между визитами без обрезки последнего слота перед закрытием; тестовая длительность для фикстур — 60 минут.

При отсутствии слотов — `NO_SLOTS`, с возможностью Relay по D-054. При ошибке чтения — доступность Relay по D-002. Неизвестное создание не является обычной ошибкой чтения.

## 5. Ссылка на слот

Предлагается stateless HMAC-подписанный токен: tenant, внутренний call reference, услуга, start/end, версия конфигурации и срок действия. Телефон/имя в токене не нужны. Base64 не шифрует содержимое; токен и времена визита не сохраняются в БД/логах.

Предлагаемый технический TTL 15 минут — **не согласованное продуктовое значение**, проверяется в локальных тестах. TTL не заменяет активность call-контекста, актуальный час до визита и повторную проверку конфигурации/занятости.

Идемпотентность основывается на стабильных полях операции, не на строке токена или его `exp`. Перевыдача того же слота не создаёт новое внешнее действие. Истёкший токен может позволять только безопасный поиск уже существующего технического результата после проверки подписи/контекста; новую операцию по нему начинать нельзя.

## 6. Создание и сверка

1. Проверить вход, активный доверенный контекст, режим, обязательные данные и отсутствие другого успешного результата этого разговора.
2. В короткой транзакции под tenant-блокировкой: найти существующую операцию, проверить постоянный booking gate, зафиксировать намерение и стабильный совместимый с Google event ID, исходный календарь и владение. Коммит **до** внешнего запроса.
3. Вне транзакции повторно проверить доступность и все актуальные ограничения; затем отправить создание с прежним event ID и техническим признаком операции. Данные визита остаются в памяти/Google.
4. Подтверждённый успех → техническое завершение и освобождение gate. Подтверждённый отказ без создания → отказ и освобождение. Неизвестный исход → сохранение запрета и сверка.
5. После успеха отдельно отправить SMS сотруднику. Его ошибка не отменяет визит и не разрешает вторую запись.

Несколько экземпляров используют согласованные версии владения. Lease и локальный request timeout не отменяют удалённый запрос. `404` не доказывает завершения предыдущего создания, `409` требует сверки, произвольный `5xx` не считается автоматически безопасным отказом. Точные гарантии проверяются на реальном API.

При неизвестном исходе приостанавливаются новые Calendar-бронирования этого автосервиса. Новые обращения допустимы через Relay, исходное неизвестное обращение — нет. Процедура: [ручная сверка](spec-booking-recovery.md).

Абсолютное исключение конфликтов с параллельными ручными действиями в Google не обещается: backend не владеет их блокировками.

## 7. Что не должно стать постоянным хранилищем

Нельзя сохранять start/end визита, контакт, описание или токен в таблицу предложенных слотов, журнал операции, полный `result_payload`, очередь, лог или audit JSON. Технические ответы в БД содержат только разрешённый результат. Время для текущего ответа берётся из валидированного запроса/подтверждённого события, не из сохранённой копии визита.
