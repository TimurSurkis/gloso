# Безопасность и эксплуатация

Статус: **проект v0.1**. Основания: D-006, D-017–D-024, D-043, D-055–D-057, D-061–D-066. Наличие мер в документе не подтверждает их реализацию.

## 1. Границы доверия

1. **Администратор Gloso:** отдельный длинный токен, HTTPS, секреты окружения. Проверка токена без утечки через timing/logs; ограничение частоты, ограничение поверхности admin API, управляемая смена токена. Не предоставлять этот токен клиентам/агенту.
2. **Инструменты агента:** аутентификация отправителя плюс подтверждённая принадлежность конкретной сессии автосервису. Общий tool-secret без привязки не доказывает права на произвольный `call_id`.
3. **События провайдеров:** реальный способ проверки подписи/возраста/повтора. Не предполагать поддержку custom secret header, HMAC или callback-полей без проверки документации и образцов.
4. **Google Calendar/SMSAPI:** наименьшие необходимые полномочия, отдельные конфигурационные привязки tenant. Ошибки provider SDK не проходят напрямую в API/логи.

Подмена tenant через модель исключается архитектурно: tenant не выбирается по тексту запроса, телефону клиента или переданному ID услуги. Все ID проверяются на принадлежность доверенному контексту. Тестовые заголовки/session resolvers невозможно включить в live-режиме незаметно.

## 2. Секреты и Service Account

- Секреты не попадают в git, миграции, seed, БД конфигурации, Telegram, tool-аргументы или примеры с реальными значениями.
- Учётные данные Google представлены в конфигурации ссылкой на профиль, а не JSON-ключом. Это позволяет разные профили без изменения use cases.
- Общий или отдельные Service Account на автосервисы ещё не выбран как эксплуатационный вариант. Предлагается предусмотреть оба способа профилями; перед пилотом выбрать конкретный и оценить радиус компрометации.
- Автосервис предоставляет доступ ровно к нужному календарю. Чтение/создание/проверка события должны быть технически возможны; backend не предоставляет функции удаления/переноса только потому, что выданные Google права шире.
- Ротация HMAC-ключей не должна превращать старую операцию в новую. Версионирование ключей/формата, окно проверки старых ключей и удаление ключей аудита описываются до реализации.
- Настройки Northflank/Neon и регионов проверяются отдельно; выбор Neon в ЕЭЗ не означает отсутствие обработки у других провайдеров за пределами ЕЭЗ.

## 3. Контакт и входные данные

Другой контакт разрешён без OTP только для новых обращений. Польский E.164 — результат нормализации/проверки структуры, не доказательство существования или владения. Caller ID также не даёт права менять визиты.

Zod проверяет строгие формы, длины и диапазоны. Доменные проверки отдельно защищают режим, текущий контекст, расписание, единственную успешную операцию и принадлежность слота. Свободный текст не используется как SQL, шаблон кода или команда инструменту.

Проект предлагает библиотеку нормализации телефонов вместо одной регулярки; конкретная зависимость и поддерживаемые типы +48 проверяются до реализации. Иностранный Caller ID сам по себе не блокируется правилом польского контактного номера.

## 4. Логи и диагностические данные

Разрешён только явный allowlist: имя модуля/маршрута без персональных параметров, безопасный код ошибки, агрегированные метрики задержки/количества, минимальная конфигурационная ссылка при необходимости.

Запрещены:

- тела запросов/ответов tools, SMS, Calendar и webhook;
- заголовки авторизации, cookies, ключи и сырые URL с query/payload;
- имена, номера/фрагменты, автомобиль, описание, время визита и токены слотов;
- автоматический лог SQL-параметров или provider error с вложенным request;
- дампы памяти/crash reports, содержащие обращение;
- аудио/транскрипции, включая попытку получить их ради отладки.

Reverse proxy/APM/платформенные логи проверяются вместе с приложением. Отсутствие `console.log(body)` не исключает утечек инфраструктурой. Точные времена сигналов и технические ссылки могут косвенно сопоставляться с аудитом; нельзя обещать невозможность корреляции.

Метрики не должны иметь номер телефона, call ID или токен как label. Детальные trace/span IDs не создают скрытую долговечную цепочку к аудиту.

## 5. Жизненный цикл процесса

Предлагаемый порядок старта: проверить конфигурацию/секреты → проверить схему и соединение → безопасная очистка истёкших данных/восстановление технического состояния → readiness → обработка работы.

Миграции запускаются явно этапом развёртывания, не конкурирующими экземплярами при каждом старте. При остановке не принимать новые операции, дождаться ограниченного завершения текущих, сохранить техническую неопределённость при неизвестном результате. Остановка Node.js не доказывает отмену внешнего запроса.

При нескольких экземплярах фоновые задачи выбирают владельца через БД. Истечение lease не является разрешением на повтор Google insert. Повторы SMS из памяти не мигрируют автоматически между процессами; их потеря при рестарте согласована.

## 6. Окружения и развёртывание

- Локальные тесты используют отдельную БД/временный PostgreSQL, не рабочий `DATABASE_URL`. Разрушающая очистка допускается только для явно созданной тестовой БД.
- Mock-адаптеры явно обозначаются в конфигурации и результатах. Live-конфигурация не принимает mock-контекст или фиктивные успехи.
- Промежуточное тестирование реального Calendar использует тестовый календарь/фиктивные обращения. Отправка SMS требует явно настроенного тестового получателя и согласованных расходов.
- Production размещается на Northflank, PostgreSQL Neon в ЕЭЗ; тарифы, регионы, TLS, пул соединений, внешние задания, резервные копии и ограничения исполнения ещё проверить.
- Для долгоживущих/фоновых задач нужно подтвердить отсутствие неподходящего scale-to-zero и достаточные лимиты соединений. Конкретный тариф не выбран.

## 7. Удаление и восстановление

Срок проверяется при каждом чтении аудита и использовании технической связи; worker не является единственной защитой. После восстановления backup приложение остаётся неготовым до очистки истёкших данных и безопасного восстановления gate.

Логическая недоступность, физическое удаление строк, сроки backup/PITR и возможное криптографическое уничтожение — разные гарантии. Независимый планировщик не гарантирует физическое удаление при недоступной БД. Строгий максимум 30 дней и восстановление без возвращения истёкших данных должны быть доказаны на выбранной инфраструктуре либо вынесены на явное изменение требований; не объявлять их выполненными автоматически.

Обработка секретов/backup после удаления клиента, конкретные сроки конфигурации и административных событий остаются пунктами ревью. Для первого релиза не вводить безусловный `DELETE` всей истории tenant, обходящий неизвестные внешние операции.

## 8. Наблюдаемость и сигналы

Readiness, ошибки БД, задержки допусков/tools, число неизвестных исходов, возраст gate, ошибки/исчерпание повторов SMS, успешность очистки и просроченные задания должны быть наблюдаемы без содержимого звонков.

Telegram — канал технических сигналов, не гарантированное хранилище задач и не замена независимому мониторингу. При полном падении backend сигнал должен исходить от внешнего мониторинга, а не от неработающего приложения. Согласовать можно конкретный мониторинг перед развёртыванием; не добавлять молча новый сервис, получающий персональные данные.

Перед живым запуском технический проект становится основанием для обновления `regulamin.html` и `polityka-prywatnosci.html`. В том числе нужно проверить описание псевдонимного состояния, конфигурационных контактов, Telegram, регионов, ретенции внешних AI-провайдеров и отсутствие у backend аудио/транскрипций. Это отдельная проверка, не юридическое заключение документа.
