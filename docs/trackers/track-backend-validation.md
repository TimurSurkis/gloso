# Проверки и блокеры живого пилота

Статус: исходный список v0.1. **Ни одна проверка ниже не считается выполненной только по наличию описания.** На момент интервью есть тестовый Google Calendar и агент ElevenLabs; Twilio (голос и SMS) ещё не подтверждён. Ключи, тела реальных обращений и секреты сюда не добавляются.

По каждой проверке требуется результат, дата, безопасная ссылка на документацию/протокол теста и принятое решение. При несовместимости с согласованным требованием не менять его молча: задать владельцу один конкретный вопрос.

## V-01. Допуск ДО запуска AI и независимый маршрут отказа — критический

- [ ] Проверить, где на реальном маршруте Twilio → ElevenLabs можно запросить backend до подключения/начала тарификации AI.
- [ ] Отдельно проверить нативную интеграцию ElevenLabs с Twilio: не подключает ли она агента в обход backend. Если допуск до AI невозможен, маршрут не допускается к пилоту.
- [ ] Подтвердить запрет при отказе/тайм-ауте/недоступности backend и БД.
- [ ] Проверить сообщение телефонии без AI для занятого AI, недоступного пилота и технического отказа.
- [ ] Проверить отсутствие петель, реальные задержки неответа/занятой линии, работу после закрытия.
- [ ] Если выбранный способ (Twilio Studio/Function, SIP-транк или иной) этого не позволяет, описать доказанную альтернативу для отдельного согласования. Не выдавать отказ tool API после старта за выполнение допуска.

## V-02. Доверенный контекст и события Twilio/ElevenLabs — критический

- [ ] Установить, какие метаданные номера назначения, агента, CallSid/conversation ID действительно доступны серверу и проверяемы.
- [ ] Проверить подпись запросов Twilio, возраст, порядок, повторы, ключи событий и ограничения повторной доставки; не предполагать поддержку без проверки.
- [ ] Проверить механизм привязки tools к конкретному допуску; не доверять аргументам LLM и одному общему secret.
- [ ] Найти технические источники факта подключения AI и точной длительности, включая нулевые/прерванные/поздние события.
- [ ] Убедиться, что backend **не получает аудио/транскрипции**. Если webhook содержит их обязательно, отбрасывание после получения не равно этому требованию: нужен другой metadata-only механизм либо отдельное изменение требований.
- [ ] Проверить доступность реальных tool timeout и нормализованных ответов без изменения промптов в этой задаче.

## V-03. Ограничение и завершение разговоров — критический

- [ ] Подтвердить максимум 180 секунд на реальном маршруте и момент отсчёта AI-длительности.
- [ ] Проверить второй одновременный звонок одного tenant и независимость разных tenant.
- [ ] Определить доказательство завершения при потерянном webhook; lease в БД не равен окончанию удалённого звонка.
- [ ] Проверить конец пилота/минут во время разговора: не обрывается по балансу, следующий старт запрещён.

## V-04. Google Calendar — критический

- [ ] Настроить тестовый Service Account и реальные права чтения/создания/проверки событий.
- [ ] Выбрать эксплуатационный профиль учётных данных (общий или раздельные), проверить изоляцию tenant.
- [ ] Проверить busy/freebusy, ручные/прозрачные/повторяющиеся/целодневные события, временные зоны и DST.
- [ ] Проверить формат стабильного event ID, технический признак операции, `insert/get`, `404/409/5xx` и запаздывающее создание.
- [ ] Подтвердить безопасную классификацию отказов, не выдавать тайм-аут за отсутствие записи.
- [ ] Проверить отзыв доступа/изменение конфигурации при неизвестной операции в исходном календаре.

## V-05. Twilio Programmable Messaging — критический для Relay

- [ ] Создать/настроить аккаунт, отправителя для Польши и тестового получателя; секреты отдельно.
- [ ] Проверить доступность номера/отправителя: long code, short code, alphanumeric sender ID и требования регистрации в Польше. Не считать отправку возможной без подтверждения.
- [ ] Проверить принятие против доставки, временные/постоянные/неизвестные исходы и подписи status callback.
- [ ] Проверить реальную поддержку идемпотентности/сверки; до подтверждения неизвестный исход не повторяется. Message SID сам по себе не доказывает отсутствие дубля.
- [ ] Проверить кодировку польского текста, сегментацию, максимальные длины, ограничения/стоимость и тайм-ауты.
- [ ] Испытать повторы только в памяти и потерю незавершённой отправки при рестарте без скрытой очереди.

## V-06. Состояние, сроки и replay — критический

- [ ] Обосновать техническое окно до 7 дней реальными окнами доставки/возраста событий. Если недостаточно, вынести изменение на согласование.
- [ ] Проверить однократный расход, позднее завершение и отказ старому событию после удаления ключа дедупликации.
- [ ] Проверить минимальный `RECOVERY_REQUIRED` без удалённых ID и без автоматического разрешения новой брони.
- [ ] Проверить часовую точность аудита, отсутствие точных скрытых timestamps/связей в логах и вспомогательных таблицах.
- [ ] Описать точную политику удаления данных и конфигурации, включая backup/PITR и восстановление.

## V-07. Northflank/Neon и Telegram — критический до размещения

- [ ] Подтвердить регионы, тарифы, runtime, сетевой доступ, TLS, соединения PostgreSQL и исполнение фоновых заданий.
- [ ] Проверить доступность независимой очистки/мониторинга и реальные гарантии удаления/backup.
- [ ] Создать Telegram-бота/получателя, не записывая токены в документы; проверить фильтрацию/частоту/неизвестный исход отправки.
- [ ] Проверить все инфраструктурные логи/APM на отсутствие данных обращений и секретов.
- [ ] Выполнить восстановление из backup до readiness без возвращения просроченного аудита/связей.

## V-08. Согласование документов и выпуск — критический

- [ ] Провести ревью проекта таблиц, собственных API и предложенных алгоритмов/технических defaults.
- [x] Дата визита после окончания пилота согласована в D-067: разрешено создание во время активного пилота в пределах горизонта.
- [ ] Проверить оставшиеся проектные предложения и не принять их за согласованные требования автоматически.
- [ ] На основе финальной технической модели обновить регламент и политику: категории, цели, сроки, внешние получатели, регионы, права/безопасность и фактические ограничения.
- [ ] Заменить в юридических HTML упоминания Zadarma/SMSAPI на Twilio и обновить перечень субпроцессоров; не редактировать их до финализации технических документов.
- [ ] Проверить достижимость действующих обязательств у AI/LLM-провайдеров, отсутствие обучения, сроки аудио/транскрипций у них и metadata-only обработку backend.
- [ ] Проверить Twilio как отдельного получателя данных: регион обработки голоса/SMS, доступные EU-опции, DPA, субпроцессоры, сроки хранения логов и записей. Отразить результат в политике приватности.
- [ ] Пройти сквозные сценарии настоящим тестовым звонком до допуска живых обращений.

## V-09. Twilio: польские номера и отправители — критический до пилота

- [ ] Подтвердить доступность и стоимость польского номера +48 для голоса; требования regulatory bundle/адреса/идентификации.
- [ ] Подтвердить, что входящий звонок на номер автосервиса можно маршрутизировать через проверку допуска, а не напрямую в ElevenLabs.
- [ ] Подтвердить отправителя SMS для Польши: тип номера/alpha sender, регистрация, сроки, ограничения по содержанию и стоимости.
- [ ] Проверить поведение Twilio при недоступности backend: можно ли воспроизвести нейтральное сообщение без AI и без петли.
- [ ] Зафиксировать, какие идентификаторы (Account SID, CallSid, Message SID, номер) допустимо хранить в конфигурации/техническом состоянии, не превращая их в скрытый архив обращений.

При невыполнении критического пункта возможна локальная разработка с явно тестовыми адаптерами, **но не заявление о готовности живого пилота**.
